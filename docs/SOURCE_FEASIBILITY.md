### PAD-US owner decision required

The raw PAD-US sample must remain unchanged. Three of five returned geometries fail validity with ring self-intersections, including polygons whose bounds/intersections touch the approved geography. This affects whether an automated pipeline may safely promote and report their areas.

Options are: (1) quarantine/reject invalid shapes, preserving raw data but leaving possible protected-area coverage gaps; or (2) repair only in staging (for example, make-valid), preserve the original geometry, and record geometry type, area/topology changes and repair provenance, accepting that the repaired boundary may differ from provider geometry. Recommendation: option 2 with explicit per-feature repair audit and no promotion when repair is empty, changes an unsupported geometry type, or exceeds an owner-approved tolerance. The owner must approve the repair policy/tolerance before PAD-US is accepted for canonical screening.

### Intended ingestion patterns (not implemented)

- PAD-US: versioned USGS state package when reachable or official service query; preserve response/package and metadata, validate keys/domains and geometry before clipping or promotion.
- Annual NLCD: request only selected year and regional WCS/tile windows; store request parameters, time position, CRS, nodata, grid and checksum; do not fetch the national 41-year bundle.
- 3DEP: use TNM inventory and immutable dated tile URLs; retain checksums and vertical datum; stage/mosaic only the exact intersecting tiles and calculate within AOI windows.
- SSURGO: retain SDA/WSS query or package responses with per-SSA `saversion`/`saverest`; preserve map-unit geometry and component relations through `mukey`/`cokey`, including null/unranked ratings. If packages are used, keep original survey-area packages and clip only in staging.
- FEMA: preserve dated effective snapshots and pending products separately; attach community, panel and effective-date metadata; represent unmapped/unavailable coverage as unknown.

No application, schema, adapter, dependency or deployment implementation is represented by these patterns.
